| HAW005    | Needless Wrapper Explosion         | Wraps one API in another API with no behavioral change. LLMs frequently produce:<br>public class CustomerClientWrapper<br>{<br>    private readonly CustomerClient \_client;<br>public Task<Customer> GetAsync(int id)<br>        => \_client.GetAsync(id);<br>}<br>This is essentially the same problem as your pass-through rule, but applied specifically to wrappers/adapters/decorators.<br>The analyzer could detect a class where most public methods:<br>receive parameters<br>    ↓<br>call exactly one dependency<br>    ↓<br>forward the same parameters<br>    ↓<br>return the result<br>No transformation, caching, authorization, retry, logging, state change, or protocol conversion.<br>This should probably reuse the forwarding engine behind HAW003.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| HAW006    | Premature Generalization           | Generic/base abstractions with one concrete use. LLMs love things like:<br>public abstract class BaseProcessor<TInput, TOutput><br>{<br>    public abstract TOutput Process(TInput input);<br>}<br>public sealed class CustomerProcessor<br>    : BaseProcessor<Customer, CustomerResult><br>{<br>}<br>when there is exactly one processor.<br>Look for:<br>abstract class<br>    +<br>1 derived type<br>    +<br>no shared implementation of significance<br>and generic abstractions where every invocation uses exactly one closed generic combination.<br>That last case is particularly revealing:<br>Processor<Customer, CustomerResult><br>exists everywhere, but no other Processor<T,U> combination does.<br>That is usually speculative abstraction.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| HAW007    | Constructor Dependency Explosion   | Injects 8–15 services into one class. This one is extremely easy and valuable.<br>public OrderService(<br>    IRepository repo,<br>    ILogger log,<br>    IValidator validator,<br>    IMapper mapper,<br>    IClock clock,<br>    IEventBus events,<br>    IAuthorization auth,<br>    ICache cache,<br>    IOptions<AppConfig> config)<br>At some point, that class is doing too much.<br>Default:<br>{<br>  "HAW007": {<br>    "maxConstructorDependencies": 7<br>  }<br>}<br>I’d count actual injected service-like dependencies while excluding simple values and configuration records.<br>This catches God classes much earlier than LOC often does.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| HAW008    | Boolean Parameter Control Flow     | Methods accumulate flags controlling multiple behaviors. Generated code commonly evolves into:<br>Process(<br>    order,<br>    validate: true,<br>    notify: false,<br>    persist: true,<br>    audit: false);<br>This is dangerous because booleans often hide multiple responsibilities.<br>The analyzer can find:<br>void Process(<br>    Order order,<br>    bool validate,<br>    bool notify,<br>    bool save)<br>and increase severity when those values directly control branches.<br>A useful threshold might be:<br>1 bool parameter = fine<br>2 = warning candidate<br>3+ = error<br>Especially if each flag controls separate blocks.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| HAW010    | One-Method Service Classes         | Splits tiny operations into separate service classes. Very common AI architecture:<br>CreateCustomerService<br>UpdateCustomerService<br>DeleteCustomerService<br>GetCustomerService<br>CustomerValidationService<br>CustomerMappingService<br>Each one has 10–20 lines.<br>The names look beautifully “clean architecture,” but the maintenance surface explodes.<br>Detect classes where:<br>one public method<br>AND<br>low LOC<br>AND<br>low complexity<br>AND<br>only one caller<br>AND<br>not implementing a meaningful framework interface<br>This is a very good LLM-specific metric.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| HAW011    | Excessive Micro-Methods            | Breaks obvious logic into many trivial methods. Humans complain about large methods.<br>LLMs can go too far in the opposite direction.<br>You get:<br>ValidateCustomer(customer);<br>NormalizeCustomer(customer);<br>PrepareCustomer(customer);<br>SaveCustomer(customer);<br>NotifyCustomer(customer);<br>where each helper is:<br>private void NormalizeCustomer(Customer c)<br>{<br>    c.Name = c.Name.Trim();<br>}<br>Individually the code looks tidy. | HAW013    | Exception Laundering               | Catch exception → wrap/rethrow without adding information. This should absolutely be in Hawthorne.<br>LLMs generate:<br>try<br>{<br>    await repository.SaveAsync(entity);<br>}<br>catch (Exception ex)<br>{<br>    throw new ApplicationException(<br>        "An error occurred while saving the entity.",<br>        ex);<br>}<br>That has usually made the exception worse, not better.<br>Detect:<br>catch X<br>    ↓<br>throw new Y(..., caughtException)<br>when:<br>• nothing meaningful was handled,<br>• no relevant structured data was added,<br>• the replacement exception is generic,<br>• the caller gains no recovery information.<br>Also detect:<br>catch (Exception ex)<br>{<br>    logger.LogError(ex, "Error");<br>    throw;<br>}<br>when global logging middleware already handles it. | HAW014    | Defensive Null Checking Everywhere | Checks values Roslyn says cannot be null. | HAW100    | Abstraction Density                | Measure something like:<br>interfaces<br>\+ abstract classes<br>\+ factories<br>\+ adapters<br>\+ facades<br>\+ providers<br>\+ managers<br>\+ services<br>divided by<br>classes containing meaningful domain logic<br>Not as an immediate error.<br>Instead, Hawthorne could produce a project health metric.<br>For example:<br>Hawthorne Abstraction Density: 2.8<br>42 abstraction types<br>15 behavioral types<br>You could use it in your coding harness to detect architectural drift across AI sessions.<br>That solves a problem individual analyzers cannot: the architecture can become absurd even though every individual abstraction is justifiable in isolation.<br>The trend is more useful:<br>Commit 120     1.1<br>Commit 140     1.3<br>Commit 160     1.9<br>Commit 180     2.6<br>At that point you know the agent has started architectural inflation.<br><br>For Hawthorne specifically, I would make the next priority set HAW005 wrapper explosion, HAW006 premature generalization, HAW007 constructor dependency explosion, HAW010 one-method services, HAW013 exception laundering, HAW016 fake async, HAW021 excessive try/catch, and HAW024 CancellationToken theater.<br>Those combine high LLM frequency, significant maintenance cost, and high-confidence static detection.
